# ADR-003: 后端架构采用「领域服务（Domain Service）+ 路由（Router）」分层

> **状态**：已接受
> **日期**：2026-05-29
> **决策者**：ITOps Platform 开发团队

---

## 背景

项目从早期的"路由堆叠"（所有业务逻辑堆积在 `api/routes/*.py`）向"领域服务"架构迁移。Phase 1 建立了 `app/domains/` 目录结构，需要明确领域服务和路由之间的边界。

## 决策

采用以下分层架构：

```
HTTP Layer     → api/routes/*.py     (只做 HTTP：参数解析、响应组装、依赖注入)
Domain Service → app/domains/*/service.py (做业务流程、业务规则、跨库操作)
Data Access    → app/domains/*/repository.py (做 SQL 查询、数据映射)
```

**路由职责**：参数验证（Pydantic）→ 调用 Service → 转换响应格式
**Service 职责**：业务流程编排、事务边界、跨 Repository 协作、领域规则
**Repository 职责**：SQL 查询、ORM 操作、数据映射

## 备选方案

| 方案 | 优点 | 缺点 |
|------|------|------|
| 当前分层（选型）✅ | 职责清晰；业务逻辑可测试；模块边界明确 | 初期迁移成本 |
| 全部在 Router | 开发快 | 业务逻辑散落；难以测试；Router 膨胀 |
| DDD 完整实现 | 战略+战术全面 | 学习成本高；过度设计；不适合当前团队规模 |

## 下一步

剩余路由（旧 routes/*.py 中的逻辑）逐步向新领域迁移，遵循"先接入新 Service，再清理旧路由"的原则。
